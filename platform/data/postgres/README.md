# postgres

The platform PostgreSQL cluster, declared as CloudNativePG resources in a **separate chart from the operator**, because the custom resources need the operator's CRDs and must sync after it (Argo CD sync waves, `SkipDryRunOnMissingResource` and retries).

- **One cluster, one database and role per service:** `orders` and `payments`, created declaratively (`Database` resources and `spec.managed.roles`). The cluster name is `platform-pg`; the read-write service is `platform-pg-rw.data.svc:5432`. A bootstrap database `platform` exists but is not used by services.
- **Credentials** are never in Git: the role passwords come from the Secrets `pg-orders` and `pg-payments` generated in the cluster by the [`secrets`](../secrets) chart. The services read `orders-db` / `payments-db` in `shop`.
- **Ordering:** a PreSync gate Job (`templates/gate.yaml`, values `gate.*`) waits until the role Secrets exist before the `Cluster` or the `Database` resources are applied, because a `Cluster` applied first leaves its managed roles `pending-reconciliation`. It is the primary protection; the annotation `platform.example/reconcile-nudge` on the `Cluster` is only a fallback for a cluster already in that state ([ADR-0018](../../../docs/adr/0018-secret-generation-and-ordering.md)). `make data-check-manifests` fails if the gate is missing.
- **Profiles:** `values.yaml` (+ `values-standard.yaml`) is two instances, a primary and one replica, 5 GiB each (set `cluster.instances: 1` to go back to one); `values-ha.yaml` is three instances (required anti-affinity, so three nodes are needed), 20 GiB, larger limits.
- **Sizing (standard):** 250m / 512Mi requests, 1 CPU / 1Gi limits, `shared_buffers` 128MB.
- **Security:** CloudNativePG runs PostgreSQL as a non-root user with a read-only root filesystem, restricted-compatible. Superuser access is disabled (`enableSuperuserAccess: false`).
- **Disruption:** the operator manages the PodDisruptionBudgets of the cluster, only when there is more than one instance (`enablePDB`, a budget on a single instance would block node drains). The chart renders none of its own, so there is no second one to conflict, and `scripts/chart-contract-check.py postgres-ha` fails if one appears. The budget that protects the primary allows no voluntary disruption of it, so a node drain that has the primary on it waits for the operator or for a person to switch over; a Spot reclaim does not wait (the node goes after two minutes) and the replica is promoted. This is how the operator's documentation describes the budgets; it has not been seen on this cluster.
- **Replication is asynchronous** (`minSyncReplicas` and `maxSyncReplicas` are 0). The primary acknowledges a commit without waiting for the replica. If the primary is lost, the replica is promoted and the transactions that had not reached it are lost. The size of that window depends on the load and the network, and this chart does not give a figure. Synchronous replication would remove the loss and would stop writes when no replica can confirm them. The replica is not a backup: no backups are configured, and a mistake (a dropped table) is replicated.
- **Updates.** `primaryUpdateStrategy: unsupervised` and `primaryUpdateMethod: switchover`: the replica is updated first, then the primary is switched over to an updated replica instead of being restarted in place. With the switchover method the operator rejects an update that changes the image and the PostgreSQL parameters together, so change them in two steps. `switchoverDelay` is 300 seconds (the operator's default is an hour).
- **Placement.** The standard profile prefers different nodes (`podAntiAffinityType: preferred`) so that a cluster with fewer nodes than instances still runs them; the high availability profile requires it. The zone spread (`zoneSpread`) is `ScheduleAnyway` and `DoNotSchedule` in the high availability profile. The two volumes are separate EBS volumes, each in the zone of its pod.
- **Design and operation.** [ADR-0026](../../../docs/adr/0026-resilience-and-autoscaling.md); applying, checking and the switchover test are in the [resilience runbook](../../../docs/runbooks/resilience.md).
- **How the services reach it.** They use the read-write Service `platform-pg-rw`, which points at whichever instance is the primary; no pod name is configured anywhere (the services read the host from the `orders-db` and `payments-db` Secrets, which hold the Service name). A replica connects to the primary through the same Service (`-rw`) for streaming replication, which for the network policies means an egress rule to the Service range on 5432 and an ingress rule from the other instance's pod; both are in `platform/data/network-policies` and in the flow matrix. This is what CloudNativePG does by default; it has not been seen on a cluster.
- **Volumes:** the `Cluster` carries `Prune=false` and `Delete=false`, so neither automated pruning nor deleting the Argo CD Application removes the database or its volumes. They are removed deliberately in the teardown runbook.
- **Storage class:** `platform-data` (see [`storage`](../storage)).
