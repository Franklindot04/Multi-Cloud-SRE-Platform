# Scripts

Small helper scripts used by the Makefile, CI and local development. Shell scripts are linted with `scripts/shellcheck.sh`, which runs `shellcheck -S style` (the strictest level, so info and style findings fail) at the version CI installs (0.11.0); `make argocd-check` and `make apps-lint` both use it. Scripts must be idempotent, use `set -euo pipefail`, print usage with `-h`, and avoid embedding credentials.

- `teardown-prep.sh --context CONTEXT [--region R] [--cluster-name N] [--dry-run]`: prepares a cluster for `terraform destroy` (removes the Argo CD cluster Secret labels, deletes the Kyverno policies and webhook configurations (only those whose names start with kyverno) and the External Secrets objects and webhook configurations (only `secretstore-validate` and `externalsecret-validate`), then deletes the CloudNativePG `Database` objects and `Cluster`, the `RabbitmqCluster` and the claims, waits for the metrics foundation's pods and deletes its claims if its namespace exists, and checks volumes, load balancers and security groups; 16 steps, listed in the script header and the runbook). When an operator is already gone, it removes the one operator finalizer from a stuck `Database` or `RabbitmqCluster` and says so; any other finalizer is left alone and the script stops. It clears no Prometheus Operator finalizer: the operator sets none in this configuration (see [ADR-0020](../docs/adr/0020-metrics-stack.md)). See the [data layer runbook](../docs/runbooks/data-layer.md#teardown) and its note on a namespace stuck in `Terminating`. Tested against a fake `kubectl` and `aws` in `scripts/tests/fakes` by `scripts/test-scripts.sh`. Before step 1 it warns (and does not fail) about what `scripts/chaos-run.sh --cleanup` would find; it removes the `argocd.argoproj.io/skip-reconcile` annotation from any Application that carries it (a paused Application is not processed, deletion included) before it waits for the Applications; and it deletes the chaos load helper's pod and policy in `shop` before it waits for the namespace. The step counts (16, or 13 with `--skip-aws`) are unchanged.
- `teardown-argocd.sh --context CONTEXT [--timeout S] [--dry-run]`: runs after `teardown-prep.sh` and before `terraform destroy`. Refuses to start while a persistent volume or a claim in the `data` namespace, a Kyverno policy, a Kyverno webhook configuration, an External Secrets object or an External Secrets webhook configuration is left, deletes the `data`, `shop` and `observability` namespaces and the `platform-data` storage class, deletes `platform-root` and the ApplicationSets, waits for the Applications, runs `helm uninstall argocd` (a missing release is fine) and deletes the `argocd` namespace; 11 steps, listed in the script header. When the application controller is no longer running, it removes the one finalizer `resources-finalizer.argocd.argoproj.io` from Applications that are stuck on it and from the AppProjects left, with a guarded patch, and says so; it never forces and touches no other finalizer. See the [Argo CD runbook](../docs/runbooks/argocd.md#teardown). Tested against a fake `kubectl` and `helm` by `scripts/test-scripts.sh`; not yet run against a real cluster. It also removes the `argocd.argoproj.io/skip-reconcile` annotation from every Application that has it, as the first thing in the step that deletes `platform-root` (the 11 steps are unchanged).
- `chart-contract-check.py` and `python-with-yaml.sh`: contract checks run by `data-manifests-check.sh`, `deploy-check.sh`, `observability-check.sh` and `argocd-check.sh` (no hook-only chart, no Helm-hook Job that creates Secrets, the PostgreSQL PreSync gate, the sync-wave order of the data and observability ApplicationSets; for the metrics foundation also restricted Pod Security, no persistent storage, Grafana's admin Secret, digest pinning, the Prometheus Operator CRDs and the fit with the AppProject).
- `network-policy-flows.py [--profile NAME] MATRIX NAMESPACE:FILE...` and `network-policies-check.sh`: the offline check of the network policies (`make network-policies-check`). The script renders the policies and the charts they select, runs the policy contract and the label check of `chart-contract-check.py`, and then the flow evaluator, which implements the standard NetworkPolicy semantics and evaluates every flow of [`tests/fixtures/network-policies/flows.yaml`](tests/fixtures/network-policies/README.md) (allowed and denied) against the rendered policies, for the data and the memory profile of the services. The evaluator models how the agent matches egress for a Service (against its ClusterIP, with the ingress side matched against the pod), as it was observed on a cluster on 2026-11-02. It proves the policies mean what we intend, not that the policies of this version work on a cluster, which has not been tried; see [ADR-0024](../docs/adr/0024-network-policies.md) and the [network policy runbook](../docs/runbooks/network-policies.md). Its unit cases and mutation cases are in `test-scripts.sh`.
- `seed-secrets.sh` and `secrets/manifest.yaml`: generate the platform's secret values and write them to AWS Systems Manager Parameter Store as SecureStrings (standard tier, the AWS-managed key `alias/aws/ssm`) under `/<prefix>/<environment>/<component>/<name>`, for example `/multi-cloud-sre/dev/postgres/orders-password`. The manifest lists each secret by name, length, character set and consumers, never a value, and is the single source for the script; the External Secrets definitions are checked against it. Usage: `scripts/seed-secrets.sh --region eu-north-1` creates the parameters that are missing and never changes one that exists (`put-parameter --no-overwrite`); `--check` lists which exist and which are missing and exits 1 if any is missing (it uses `describe-parameters`, which returns no value); `--purge` deletes every parameter under the path after you type the environment name (there is no `--yes`); `--dry-run` makes no AWS call. Options `--environment` (default `dev`), `--prefix` (default `multi-cloud-sre`, the Terraform variable `secrets_parameter_prefix`) and `--profile`. A value is held in a shell variable and written with the `printf` builtin to a JSON file that the AWS CLI reads (`--cli-input-json file://<path>`; the CLI does not accept the JSON from a pipe), so it is in no command line and no output, and the script never reads a value back. The file is in a directory made for the run (`mktemp -d` under `umask 077`, mode 0700), is mode 0600, and is deleted straight after each call; the directory is removed on exit, interrupt, termination and hangup. This does not erase the value: the value exists on disk for a moment, in a directory only the owner can read, and the file is deleted straight after use. A failed call prints the AWS error code and the exit status of the CLI, never its message. Terraform creates no parameter: the role of the External Secrets Operator (`infra/terraform/modules/aws-external-secrets-iam`) only reads the path. Tested in `test-scripts.sh` against a fake `aws`; it has not been run against AWS.
- `external-secrets-check.sh`: the offline checks of the External Secrets Operator under `platform/security` (`make external-secrets-check`): chart lint, render and schema checks for the operator, the ClusterSecretStore and the network policies of the `external-secrets` namespace, the contracts (`chart-contract-check.py external-secrets`, `eso-store`, `priority`, `project-fit`, `network-policies`), the refusal to render without the role, the region and the parameter path, and the ServiceMonitor of the monitors chart. Run by `.github/workflows/external-secrets.yml`; nothing is installed in a cluster.
- `rollout-analysis-test.py`: builds the promtool test file for the queries of the canary analysis from the rendered AnalysisTemplate and `deploy/helm/tests/analysis-queries.test.yaml` (run by `observability-check.sh`).
- `chaos-run.sh` and `chaos-run.py`: run a chaos experiment from `chaos/experiments` (a dry run by default; `--execute` after typing the cluster name; `--validate` for the schema; `--cleanup` for leftovers). The shell script is a wrapper; the Python parses the experiment, checks every change against its blast radius, watches the probes, always rolls back, and writes a result. Needs no AWS credentials. See [`chaos/README.md`](../chaos/README.md).
- `chaos-load.sh`: starts and stops a small steady request load against the gateway from a throwaway restricted pod in `shop`, with a temporary NetworkPolicy that lets only that pod in (about two requests a second, an order every fourth, ends by itself, refuses a cluster that is not a dev cluster). The chaos experiments need it. See [`chaos/README.md`](../chaos/README.md).
- `chaos-lint.py`: lints the chaos experiments against the platform: every metric in a probe exists in the rules, the confirmed list, a dashboard or `chaos/metrics-allowlist.txt`, every alert exists, the blast radius is no wider than the injection; can write the probe queries for `promtool check rules`.
- `chaos-tests.sh` and `chaos-check.sh`: the tests of the chaos runner and the load helper, against a fake `kubectl` and a fake Prometheus (`scripts/tests/fakes/chaos`), including a dry run and a run of every experiment against a simulated cluster, and the check that CI runs (`make chaos-check`): the experiments against the schema and the lint, promtool on every probe query, `yamllint`, the tests and `shellcheck`. `test-scripts.sh` runs the tests as well.
- `delivery-check.sh`: the offline checks of the Argo Rollouts controller under `platform/delivery` (`make delivery-check`): chart lint, render and schema checks for the controller (default and two-replica values) and the network policies of the `argo-rollouts` namespace, the contracts (`chart-contract-check.py argo-rollouts`, `restricted`, `priority`, `project-fit`, `network-policies`), the refusal to render without the Service range, the agreement of the bootstrap flag, the cluster label and both ApplicationSets, a check that the committed render in `scripts/tests/fixtures/delivery` is still the real one, and the ServiceMonitor of the monitors chart. Run by `.github/workflows/delivery.yml`; nothing is installed in a cluster.
- `policy-check.sh` and `policy-test-inputs.py`: the offline checks of the Kyverno install and the admission policies under `platform/security` (`make policy-check`): chart lint, render and schema checks, the contracts (`chart-contract-check.py kyverno`, `policies`, `project-fit`, `network-policies`), the Kyverno ServiceMonitor, and, with Docker, the Kyverno CLI at the version of the chart's app (the image the chart's hook Job uses, pinned by digest): `kyverno test` on [`platform/security/policies/tests`](../platform/security/policies/tests), a check that those tests can fail, and the reality check, which renders the service chart under every profile and cloud and the RabbitMQ credentials chart and runs the policies over them. `policy-test-inputs.py` writes the inputs of those tests. Run by `.github/workflows/policy.yml`.
- `logql-check.py LOKI_URL DASHBOARD_DIR`: runs every Loki query of the Grafana dashboards against a running Loki, with sample lines in the shapes the services log, and checks what comes back; started by `observability-check.sh`.
- `trace-check.py TEMPO_URL COLLECTOR_URL`: sends one trace to a collector and looks for it in Tempo; started by `observability-check.sh` with containers made from the rendered configuration.
- `observability-check.sh`: offline checks of the metrics and logging stack under `platform/observability` (`make observability-check`): chart lint, render and schema checks, the operator's CRDs, vendored chart pinning, the contracts above, and, when Docker is running, the collector, Loki and Alloy configurations validated with their images, the dashboards' LogQL run against a Loki container (`logql-check.py`), and a trace sent to a collector and found in a Tempo container (`trace-check.py`); it also checks the Tempo configuration and the Grafana data sources. Run by `.github/workflows/observability.yml`. It also lints and unit tests the delivery rules (the alerts on canary rollouts) with promtool, checks the delivery alerts against the progressive delivery runbook (`chart-contract-check.py delivery-rules`), and runs the two queries of the canary analysis against synthetic series.
- `verify-image.sh SERVICE|all [DIGEST]`: checks the signature, the SBOM attestation and the build provenance of a published image with cosign, pinned to the images workflow on `main` of this repository and the GitHub OIDC issuer; prints PASS or FAIL per check and per image and exits non-zero on any failure. See [verify an image](../docs/runbooks/service-deployment.md#verify-an-image). Tested against a fake `cosign` in `scripts/tests/fakes`, and run against the real signatures of the published images.
- `check-trivyignore.sh [FILE]`: checks `.trivyignore` before an image scan: every entry needs a `# reason:` line directly above it and an unexpired `exp:YYYY-MM-DD` date. Run by the images workflow and tested by `scripts/test-scripts.sh`.
