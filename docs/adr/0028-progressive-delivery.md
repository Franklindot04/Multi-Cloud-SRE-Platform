# ADR-0028: Progressive delivery with Argo Rollouts

- Status: Accepted
- Date: 2026-11-02

## Context

The sample services are deployed as plain Deployments with a rolling update. A rolling update replaces pods a few at a time and stops only if the new pods fail their probes. It cannot look at the error rate or the latency of the new version, it cannot send a share of requests to it, and it cannot go back by itself when the numbers are bad. The platform already has what such a decision needs: Prometheus, the SLO recording rules and the alerts of [ADR-0023](0023-slos-and-alerting.md).

It is decided in three steps: the controller and its platform wiring, the gateway as a canary Rollout with an analysis on Prometheus, and the alerts, the dashboard and the runbook. **Nothing in them has run on a cluster.**

## Decision

The platform adopts Argo Rollouts, as an opt-in add-on in the way of Kyverno ([ADR-0025](0025-admission-policies.md)) and the External Secrets Operator ([ADR-0027](0027-external-secrets.md)): a wrapper chart over the official chart, a cluster label that switches it on, a bootstrap flag that sets the label, and a check script and workflow of its own.

### Why Argo Rollouts

- **It belongs to the tools already in use.** Argo CD is the deployment tool, and Rollouts shows its state in the same way (health, a paused rollout, a degraded one).
- **Canary and blue-green without a mesh.** It splits traffic by replica count when no traffic router is configured, which is what this platform has: no service mesh and no ingress controller with weighted routing. A mesh would be a much larger decision.
- **Analysis reads Prometheus.** An analysis run queries the metrics the platform already collects, and a failed run aborts the rollout.
- **A Rollout replaces a Deployment, it does not wrap it.** The pods are ordinary pods of ReplicaSets, so the admission policies and the network policies of the `shop` namespace apply as before (see below).

### Why opt-in

It adds a controller and five CRDs of about 230 KiB each, requests of 50m CPU and 64Mi of memory, and a new thing to break. On a cluster that runs plain Deployments none of that earns anything. The label `platform.example/progressive-delivery` and `scripts/bootstrap-argocd.sh --enable-progressive-delivery` switch it on; it is off by default, and the teardown scripts remove the label with the others.

### The controller

- **The chart.** `argo-rollouts` 2.43.8, application v1.10.1, from `https://argoproj.github.io/argo-helm`, pinned in `Chart.yaml` and `Chart.lock`, in `platform/delivery/argo-rollouts`. A new `platform/delivery` folder, because the add-on belongs neither to the security nor to the observability group.
- **Kubernetes 1.37 is not confirmed.** The chart has no `kubeVersion`, the project states no supported range, and its end-to-end tests for v1.10.1 run against 1.32 to 1.35. The cluster runs 1.37. The controller uses core APIs and its own CRDs, so nothing is known to break, but that is a guess, and the README says so.
- **One replica, no dashboard, no notifications, no traffic-router rights, no webhook.** The reasons are in the chart README. In short: the room left on the nodes is small ([resilience runbook](../runbooks/resilience.md)); a stopped controller leaves the existing Rollouts and their traffic as they are and only stops the progress of a rollout in flight; and the other three are features nothing uses. `values-ha.yaml` holds the two-replica setting for when it matters.
- **Restricted and small.** The `argo-rollouts` namespace is created at the `restricted` Pod Security level; the pod is non-root, with a read-only root filesystem, no privilege escalation, `RuntimeDefault` seccomp and all capabilities dropped. Requests are 50m and 64Mi; limits 200m and 192Mi. The priority class is `platform-addons-critical`.
- **Argo CD.** Two ApplicationSets, `99-delivery-argo-rollouts` (sync wave 18) and `100-delivery-network-policies` (wave 19). The numbers follow 98 (the last observability file) and the waves follow the observability stack (10 to 17) and come before the services (20). A wave only orders the creation of the ApplicationSets, not the sync of what they make, so the policies being after the controller is a convention, as for the other add-ons. The controller syncs with `ServerSideApply=true`, because its CRDs are close to the size client-side apply can store.
- **The AppProject.** `platform-addons` gets one new destination, the namespace `argo-rollouts`. Every kind the chart renders was already allowed, so no kind is added and nothing else is widened.
- **Network policies.** Default deny, then DNS, the Kubernetes API (TCP 443 to the Service range) and the scrape by Prometheus on 8090, as [ADR-0024](0024-network-policies.md) found necessary on the VPC CNI. The controller also may query Prometheus on 9090, which it does to run the analysis of the gateway canary. No rule takes the VPC range, because the controller has no webhook and nobody connects to it but Prometheus.
- **Monitoring.** A ServiceMonitor in the `monitors` chart selects the metrics Service.
- **Checks.** `scripts/delivery-check.sh` and `.github/workflows/delivery.yml` (path filtered) build the chart and run the contracts; `scripts/test-scripts.sh` runs the same contracts on a committed render and breaks each rule on purpose.

### The gateway as a canary

- **Rollout mode in the service chart.** `rollout.enabled` (default `false`) renders an Argo Rollout in place of the Deployment, from one shared pod template (`service.podTemplate`) that the Deployment also uses, so the labels, selector, probes, security context, resources, priority class and topology spread cannot drift. A contract check compares the two renders. The Deployment render of every service is the same as before, except that an empty `volumeMounts:` line is no longer written (the schema of the Rollout does not accept a null list).
- **A canary with no traffic router.** There is no ingress controller with weighted routing and no service mesh, so a step's weight is a share of the **replicas**, and the Service sends requests to all ready pods, stable and canary. The split is approximate and depends on the replica count (2 replicas at 25 percent is 1 canary pod and 1 stable pod, about half of the requests). This is the main limit of the design, and a real traffic router would remove it; it is not worth a mesh for four services. The steps are values: 25 percent, a 5-minute pause, 50 percent, a 5-minute pause, then promotion.
- **What stays as it was.** The Service and the PodDisruptionBudget select the labels both revisions share. The autoscaler targets the Rollout, which has no `replicas` field then, as the Deployment had none. `maxUnavailable` is 0 and `maxSurge` 50 percent, within the budget of 1. A progress deadline of 600 seconds aborts the rollout, and an abort sets the canary weight to zero, which scales the canary down. `abortScaleDownDelaySeconds` is not used: the project documents it only for a canary with a traffic router.
- **The analysis.** A background AnalysisTemplate with two metrics from the series the SLOs use: the share of requests that are not server errors, and the share that finish within 0.5 s, each on the canary pods only. The pods are told apart by name: the Rollout passes the pod template hash of the new revision (`podTemplateHashValue: Latest`) and the query selects `pod=~"gateway-<hash>-.+"`. The `pod` label comes from the ServiceMonitor, and the thresholds are the SLO objectives with a margin: 0.99 against 99.5 percent, and 0.90 against 95 percent, because two minutes of traffic is a few requests and one slow request must not abort a rollout. Failure needs more than two bad measurements.
- **No traffic is inconclusive.** A measurement is made only when the canary served at least 20 requests in the window; below that, or without series, the query returns NaN. Success is `>= T` and failure is `< T`, so NaN is neither, and the measurement is inconclusive. After more than two such measurements the run is inconclusive and the rollout pauses at its step until a person promotes or aborts it. In plain words: an idle dev cluster neither promotes a canary it has not seen nor aborts one for lack of data. The analysis decides before the timed pauses run out (a check fails the chart otherwise), or the pauses would promote the canary by themselves. If Prometheus cannot be queried, the run errors after three tries and the rollout is aborted: it fails closed.
- **Gated on the cluster.** The gateway ApplicationSet sets `rollout.enabled` only when the cluster has the label `platform.example/progressive-delivery`, only in the data profile, and `rollout.analysis.enabled` also needs the label `platform.example/observability`. The memory profile and clusters without the controller render the Deployment. The `platform-apps` AppProject allows two kinds of `argoproj.io`, `Rollout` and `AnalysisTemplate`, and nothing else of the group.
- **Why the gateway only.** It keeps no state and every request is forwarded, so two revisions side by side are safe, and its series are the ones the SLOs measure. Orders stays a Deployment: its work is the outbox relay and the order state, which a request-ratio analysis does not see, so a canary of orders needs a different analysis (the backlog and age of the outbox, the dead-letter count) and a decision about two revisions claiming outbox rows. Payments and the notifier have no SLO series and keep state per pod.
- **Argo CD health.** Argo CD v3.5.6 has built-in health checks for `Rollout`, `AnalysisRun` and `Experiment` (`resource_customizations/argoproj.io` in its source): a Rollout is Progressing while it steps, Suspended while it is paused (a pause or an inconclusive analysis), Degraded when it is aborted or passes its deadline, and Healthy when it is complete. An `AnalysisTemplate` has no status and no check, so it is shown as Healthy. No custom health check was added. No `ignoreDifferences` is needed: the Rollout has no `replicas` field when the autoscaler is on, as the Deployment had none, and the controller changes status only. The Application shows Suspended during a pause, which is expected. None of this was seen on a cluster.
- **Kyverno.** `require-probes` now also matches `rollouts` (`argoproj.io/v1alpha1`). The other five match pods, and the pods of a Rollout are ordinary pods, so they apply as before. The difference is when: a Deployment is checked on apply through autogen, which Kyverno does not have for a Rollout, so in `Enforce` a bad Rollout would be accepted and fail when its ReplicaSet creates a pod. Everything is still in Audit, so there is no difference today. The policy tests have Rollouts and pods of Rollouts, and the reality check renders the gateway as a Rollout.

### Alerts, dashboard and runbook

- **Seven alerts**, all tickets (the `delivery` rules in the monitors chart): `RolloutAborted`, `RolloutDegraded` (the phases `Timeout`, `Error` and `InvalidSpec`), `RolloutPausedTooLong` (30 minutes: a pause that waits for a person), `AnalysisRunFailed`, `AnalysisRunError` (a metric of a run could not be measured, which includes Prometheus not being reachable), `RolloutsControllerDown` and `RolloutsControllerNotReconciling`. None pages: in every case the stable pods keep serving (an aborted canary is scaled down, a paused rollout leaves the old pods, a dead controller leaves the existing pods alone), and a canary that fails requests burns the SLO, whose alerts page. They are on state and so resolve with it; the two on analysis runs stay until the run is removed, which the runbook says.
- **The metrics** are the controller's own (`rollout_info`, `analysis_run_info`, `analysis_run_metric_phase`, `rollout_reconcile_error`, `analysis_run_reconcile_error`), taken from its documentation and source at v1.10.1, because the names and labels are not in the chart. They are confirmed in `dashboards/confirmed-upstream.txt`, and not seen on a cluster. The documentation lists the names but not the labels or the phase values; those are from the source (`controller/metrics`).
- **A defect found while writing them, in the ServiceMonitor of the controller.** The rollout metrics carry the namespace of the Rollout in the label `namespace`. A ServiceMonitor without `honorLabels` makes Prometheus rename that label to `exported_namespace` and put the namespace of the controller in `namespace`, so every selector on `namespace="shop"` would have matched nothing, in the alerts and the dashboard. The ServiceMonitor now sets `honorLabels: true`, and `scripts/delivery-check.sh` fails without it. This is reasoned from how Prometheus treats conflicting labels and has not been seen on a cluster; the runbook has the query that shows it.
- **A dashboard,** `sre-delivery` (Progressive delivery): the rollouts by phase, whether the controller is up, failed analysis runs, reconcile errors, the phase and the replicas of each Rollout over time, and the analysis runs with the result of each metric. It uses only metrics confirmed in that list.
- **The runbook** ([progressive delivery](../runbooks/progressive-delivery.md)) covers switching it on, how a release flows, watching, promoting, aborting, retrying and rolling back, a good, a bad and an idle test release (the bad one with the fault settings the gateway already has, so no change to the application), what each alert means, the limits and the teardown, and it ends with the checks for the next apply session for everything merged and not yet run on a cluster.

### The admission policies

The six policies of [ADR-0025](0025-admission-policies.md) apply to the namespace `shop` only, so the controller itself is outside them. What was done for Rollouts is in the list above.

## Alternatives considered

- **Flagger.** Similar in purpose, and it keeps the Deployment. It leans on a mesh or an ingress controller for traffic shifting, which this platform does not have, and it is a second tool beside Argo CD instead of a sibling of it.
- **Argo CD alone, with sync waves and hooks.** It orders resources; it does not watch metrics or shift traffic.
- **Plain Deployments.** Simple and enough while the services have no users who notice a bad release. Kept as the default.
- **A service mesh for traffic shifting.** Precise weights and header routing, at the cost of a sidecar or ambient layer on every pod. Not worth it for four services.

## Consequences

- **A new thing that can be down.** Existing rollouts keep running; one in progress stops, and the new version is neither promoted nor aborted until the controller is back.
- **The CRDs outlive the chart.** `keepCRDs` is true so that removing the chart cannot delete every Rollout in the cluster. The teardown scripts do not remove them; they go with the cluster. The teardown needs no new step: the gateway Rollout is deleted with its Application, its ReplicaSets and pods follow through their owner references (the wait for an empty `shop` namespace already lists pods), and we found no finalizer that the controller puts on its own objects. The wait does not list `rollouts` itself, because asking for a kind whose CRD is already gone is an error. None of this was tested on a cluster. The label comes off with the others and the script waits for the `delivery-*` Applications.
- **Canary weights are replica counts.** With few replicas the steps are coarse; five percent of two pods is not possible, and 25 percent of two is half. A canary that has served little traffic is judged on few requests, which is why the thresholds have a margin and the measurement a minimum count.
- **A paused rollout needs a person.** An inconclusive analysis stops the rollout for good until it is promoted or aborted. That is the intended answer to no data, and the [runbook](../runbooks/progressive-delivery.md#promote-abort-retry-and-roll-back) says how.
- **A guess about Kubernetes 1.37.** It is recorded and has to be proven on a cluster.

## What is proven and what is not

Proven offline: the chart lints, renders (default and two-replica) and passes kubeconform; the contracts for Pod Security, requests and limits, the priority class, leader election, the CRDs against server-side apply, the fit with the AppProject, the ServiceMonitor against the real metrics Service, and the agreement of the label, the flag and both ApplicationSets; the network policies and the flow matrix for both profiles; the teardown scripts against a fake `kubectl`.

For the gateway canary: the Rollout render has the same pod template, selector, replicas and objects as the Deployment render, the autoscaler targets it, and it passes the security, network policy, scaling and AppProject checks and the schema of the Rollout and the AnalysisTemplate (kubeconform, with the schemas of the CRD catalog the repository already uses); the contract refuses a Rollout without a deadline or steps, a metric without a failure condition, a query on all pods, a query without a no-data value or a minimum, and pauses shorter than the analysis. The two queries were run by promtool against synthetic series: all good, canary failing, canary slow, and four kinds of no traffic (idle, not scraped yet, too little traffic, only client errors), and the tests were shown to fail on a query that reads the stable pods or has no no-data value. The Kyverno CLI evaluated the probe policy on Rollouts and the pod policies on the pods of a Rollout. **What the PromQL tests do not show:** that Prometheus has the `pod` label on these series (read from the operator's source, not seen), that Argo Rollouts treats a NaN as inconclusive as its documentation says, that `increase()` over two minutes behaves with the real scrape timing (the tests use a 30-second step and ratios that do not depend on the extrapolation), or what a real canary does with the replica split.

**Not proven on a cluster:**

- The controller starting and staying healthy under the `restricted` level, on Kubernetes 1.37.
- Prometheus scraping it through the VPC CNI policies, and the controller reaching the API server through the Service range.
- Server-side apply of the five CRDs by Argo CD.
- The recovery time after a node loss with one replica.
- A gateway canary: the replica split, the pod hash in the pod names, the `pod` label on the series, an analysis that fails a bad canary, pauses on no data, the abort and the scale-down, the Argo CD health of a paused or aborted Rollout, the switch of an existing Deployment to a Rollout, and the HPA driving a Rollout.
